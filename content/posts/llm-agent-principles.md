> **说明：** 本文基于近期论文与行业实践整理，主要写给「已经用过 ChatGPT/Copilot 这类产品、但想知道 agent 到底怎么跑起来」的读者。撰写时参考了 arXiv 上的多篇 agent 综述与架构论文（2024–2026 年），文末附有主要参考。

## 一、LLM 本身能做什么，不能做什么

先对齐一个基本认知：**LLM 是一个给定输入、预测下一个 token 的模型**。你给它一段文字，它续写出下一段。训练完之后，它的「知识」就固定在参数里了，不会自己更新。

这意味着，单独一个 LLM 有几件做不了的事：

1. **不能主动获取新信息**。它不知道今天的天气、你刚才改了哪行代码、GitHub 上最新的 issue 是什么。
2. **不能执行动作**。它只能输出文本，不能真的去跑一个命令、发一个请求、写一个文件。
3. **不能长期记忆**。每次对话都是独立的（除非你把历史塞进 prompt），它不记得上周你们聊过什么。
4. **不能拆解复杂任务**。它可以一步步推理，但不会自己决定「先做 A、再做 B、发现 B 不行就换成 C」这种动态计划。

而 **Agent** 就是给 LLM 加上这几样东西之后的东西。

## 二、Agent 到底多了什么

一个典型的 LLM-based agent，大致由下面几个模块组成：

```
┌─────────────────────────────────────────────┐
│                 用户 / 环境                   │
└─────────────────┬───────────────────────────┘
                  │ 输入（任务、消息、传感器数据）
                  ▼
┌─────────────────────────────────────────────┐
│               Perception（感知）              │
│         把原始输入整理成模型能消化的格式        │
└─────────────────┬───────────────────────────┘
                  ▼
┌─────────────────────────────────────────────┐
│                Brain（大脑）                  │
│           LLM 本身：理解、推理、决策           │
│    ┌──────────┐  ┌──────────┐  ┌──────────┐ │
│    │  Memory  │  │ Planning │  │ Reasoning│ │
│    │  (记忆)   │  │  (规划)  │  │  (推理)  │ │
│    └──────────┘  └──────────┘  └──────────┘ │
└─────────────────┬───────────────────────────┘
                  ▼
┌─────────────────────────────────────────────┐
│               Action（行动）                  │
│     调用工具、执行代码、读写文件、发请求        │
└─────────────────┬───────────────────────────┘
                  │ 结果
                  ▼
              回到 Brain，
          判断任务是否完成，
          没完成就继续循环
```

**关键区别：** LLM 是「你问我答」，Agent 是「你给我一个目标，我自己跑一个循环，直到完成或者跑不下去为止」。

这个循环通常长这样：

1. 用户给一个目标（「帮我看看这个 bug 出在哪」）
2. Brain（LLM）决定下一步做什么（「先读一下这个文件」）
3. Action 模块执行（调用 `read_file` 工具）
4. 结果送回 Brain
5. Brain 决定下一步（「再搜一下相关函数」）
6. ……
7. 直到 Brain 判断「任务完成了」，输出最终结果

学术界把这个循环叫 **Observe → Think → Act**，或者更具体一点的 **ReAct**（Reason + Act）。

## 三、大脑里面到底装了啥

### 3.1 推理（Reasoning）

LLM 的推理能力，简单说就是「在输出最终答案之前，先生成一段中间思考过程」。最经典的做法是 **Chain-of-Thought（CoT）**：在 prompt 里加一句「请一步步推理」，模型就会在给出答案之前，先写出推导步骤。

这招为什么有用？因为很多任务（数学、逻辑、多步决策）需要中间状态。直接让模型给答案，它容易跳步出错；让它把过程写出来，它就能像做草稿一样一步步来。

后来出现的 **推理模型**（比如 OpenAI o1/o3、DeepSeek-R1）把这个过程内化了——它们在训练阶段就被鼓励「先想再答」，不需要你在 prompt 里提醒。

### 3.2 规划（Planning）

规划是 agent 最核心的能力之一。给定一个复杂目标，agent 需要把它拆成可执行的子任务，并且安排好顺序。

常见的规划方式：

| 方式 | 思路 | 优点 | 缺点 |
|------|------|------|------|
| **单次分解** | 把大任务一次性拆成步骤列表，然后按顺序执行 | 简单、可预测 | 遇到意外不会调整 |
| **逐步规划** | 每走一步再看下一步 | 灵活、能应对变化 | 可能陷入死循环或偏离目标 |
| **分层规划** | 先定高层策略，再填细节 | 适合复杂项目 | 实现复杂 |
| **树状搜索** | 同时探索多条路径，选最好的 | 能找到更优解 | 消耗大量 token |

实际系统里，**逐步规划 + 反馈调整** 用得最多。agent 每执行一步，都会把结果读回来，判断「这步走对了吗、下一步该干嘛」。这就是前面说的那个主循环。

### 3.3 记忆（Memory）

没有记忆的 agent，每次对话都是陌生人。agent 的记忆通常分几层：

- **工作记忆（Working Memory）**：当前对话的上下文，也就是塞进 prompt 里的所有内容。这是最短期、最直接的。
- **情节记忆（Episodic Memory）**：过去发生过的具体事件，比如「上次用户说不喜欢用 Redis」。通常存成日志或向量数据库，需要时检索。
- **语义记忆（Semantic Memory）**：抽象出来的知识和规则，比如「这个项目的鉴权走的是 JWT」。可以存成结构化文档或知识图谱。
- **程序记忆（Procedural Memory）**：怎么做某件事的技能，比如「部署这个服务要先跑 A 命令再跑 B 命令」。通常固化在 prompt 或 skill 文件里。

实际实现上，**RAG（检索增强生成）** 是最常见的记忆落地方式：把历史对话、文档、代码索引成向量，每次对话开始时检索相关片段塞进 prompt。

## 四、工具使用：Agent 的手和脚

LLM 本身只会输出文本。**工具（Tool）** 就是让它能「真的动手」的机制。

一个工具的定义通常包括：
- **名字**：`search_code`
- **描述**：「在代码库里按关键词搜索，返回匹配的文件和行号」
- **参数**：`query: string`、`limit: number`
- **返回**：一段结构化的结果

Agent 调用工具的过程：

1. Brain 根据当前状态，决定需要调用哪个工具、传什么参数
2. 框架（Agent 运行时）真的去执行这个工具
3. 工具的返回结果被塞回给 Brain
4. Brain 根据结果决定下一步

常见的工具类型：

| 类型 | 例子 |
|------|------|
| 信息检索 | 搜索代码、查文档、读数据库、查网页 |
| 代码执行 | 跑 Python、跑 shell、跑测试 |
| 文件操作 | 读文件、写文件、改文件 |
| 外部 API | 发 GitHub issue、调 Slack、查 Jira |
| 浏览器 | 打开页面、点击、填表 |

**工具选择** 是 agent 研究里的一个难点。工具太多时，光把工具描述塞进 prompt 就会吃掉大量 token；工具太少时，agent 想干的事干不了。业界常见的做法是：按任务动态加载工具列表，或者用一个小模型先筛选出可能相关的工具。

## 五、ReAct 与 Tool-Use 范式

**ReAct**（Reason + Act）是目前最主流的 agent 范式之一。它的核心思想是：**推理和行动交替进行**。

一个 ReAct 轨迹长这样：

```
Thought: 我需要先找到处理用户登录的代码文件。
Action: search_code(query="用户登录")
Observation: 找到 src/auth/login.ts，包含 handleLogin 函数。

Thought: 让我读一下这个文件，看看登录逻辑。
Action: read_file(path="src/auth/login.ts")
Observation: （文件内容……）

Thought: 问题出在第 45 行，密码没有做 hash 就直接比较了。
Action: edit_file(path="src/auth/login.ts", old="...", new="...")
Observation: 文件已修改。

Thought: 修改完成，现在跑一下相关测试确认没破坏。
Action: run_command(command="npm test auth")
Observation: 全部通过。

Thought: 任务完成。
Final Answer: 修复了登录逻辑中的密码比对问题，已添加 bcrypt hash。
```

每一步都是「想一下 → 动一下 → 看看结果 → 再想一下」。这个模式很直观，也容易调试——你可以直接看到 agent 的每一步思考。

## 六、多 Agent 协作

单个 agent 能力有限、上下文有限、一次只能干一件事。**多 Agent 系统** 把任务分给多个角色：

| 角色 | 职责 |
|------|------|
| **Orchestrator / Supervisor** | 接收用户任务，拆分、分配给下属 agent |
| **Planner** | 只负责出方案，不写代码 |
| **Coder** | 写代码、改代码 |
| **Reviewer** | 审查代码质量、找 bug |
| **Tester** | 跑测试、报告结果 |
| **Researcher** | 调研、查文档、搜资料 |

这些 agent 之间通过消息传递协作。一个 agent 的输出是下一个 agent 的输入。

多 agent 的好处：
- 每个 agent 的 prompt 更短、更聚焦
- 可以并行处理多个子任务
- 角色之间能互相检查（比如 reviewer 挑 coder 的毛病）

坏处：
- 协调成本高，agent 之间可能「鸡同鸭讲」
- 错误会传播（planner 错了，coder 跟着错）
- 总 token 消耗成倍增加

## 七、MCP：让工具接入标准化

在 MCP（Model Context Protocol）出现之前，每个 agent 框架接入工具的方式都不一样。你想让 agent 能查 GitHub？写一个插件。想接 Jira？再写一个。N 个模型、M 个工具，需要 N×M 个连接器。

**MCP 是 Anthropic 在 2024 年底提出的开放协议**，目标是把这个变成 N+M：

```
┌──────────┐         ┌──────────┐
│  LLM A   │──┐  ┌──│ GitHub   │
├──────────┤  │  │  │ MCP Server│
│  LLM B   │──┤  │  └──────────┘
├──────────┤  ├──│──┌──────────┐
│  LLM C   │──┘  │  │ Jira     │
└──────────┘     └──│ MCP Server│
                    └──────────┘
```

只要工具方提供一个 MCP Server，所有支持 MCP 的 agent 都能直接调用；反过来，只要 agent 支持 MCP，就能接所有 MCP Server。

MCP 的核心概念：

- **Host**：agent 应用本身（比如 Claude Desktop、Codex CLI、Grok Build）
- **Server**：提供工具或数据的服务（比如文件系统、数据库、GitHub）
- **Transport**：通信方式，常见的有 stdio（本地进程间通信）和 HTTP+SSE（远程服务）

Server 可以向 Host 暴露三类能力：

| 能力 | 说明 |
|------|------|
| **Tools** | 可被调用的函数，Host 决定何时调用 |
| **Resources** | 可被读取的数据源（文件、数据库记录等） |
| **Prompts** | 预定义的提示词模板，可被用户或 agent 触发 |

MCP 的出现让工具生态和 agent 生态解耦了。工具开发者不需要关心哪个模型会调用自己；agent 开发者不需要为每个工具写适配层。

## 八、Agent 为什么会失败

Agent 听起来很能干，但实际用起来经常翻车。主要失败模式：

### 8.1 工具调用出错

- **参数写错**：函数要求 `user_id: int`，模型传了 `user_id: "abc"`
- **选错工具**：该用 `search_code` 的时候用了 `run_command`
- **格式不对**：返回的 JSON 少了引号、多了逗号

研究发现，工具描述写得越清楚，agent 选对工具的概率越高。但描述太长又会吃掉太多 token，是个两难。

### 8.2 规划跑偏

- **死循环**：agent 反复执行同样的步骤，怎么都达不到终止条件
- **目标遗忘**：聊着聊着忘了最初要干嘛，开始解决一个无关的问题
- **过度分解**：把简单任务拆成太多步，每步都引入新的出错可能

### 8.3 上下文爆炸

每调用一次工具，结果就要塞回 prompt。任务越长，prompt 越长，直到超出模型的上下文窗口。常见的应对：
- 压缩历史（`/compact`）
- 只保留最近 N 步
- 把中间结果存到外部文件，需要时再读

### 8.4 安全与权限

Agent 能跑命令、能改文件、能发请求，如果权限没控制好，后果可以很严重。业界常见的做法：
- **沙箱**：限制 agent 能访问的文件和能执行的命令
- **审批**：危险操作需要人工确认（`PreToolUse` hook）
- **最小权限**：只给完成任务所需的最小权限集

## 九、评估：怎么知道 Agent 好不好

Agent 的评测比 LLM 的评测难得多。选择题有标准答案，但 agent 完成任务的方式多种多样。

常见的评测维度：

| 维度 | 测什么 |
|------|--------|
| **任务完成率** | 给定目标，agent 最终做对了没有 |
| **步骤效率** | 完成同样的任务，用了多少步 |
| **工具选择准确率** | 该选 A 工具的时候有没有选对 |
| **鲁棒性** | 输入稍有变化，还能不能完成 |
| **安全性** | 会不会执行危险操作、泄露敏感信息 |

代表性的 benchmark 有 WebArena（网页操作）、SWE-bench（真实 GitHub issue 修复）、ToolBench（工具使用）等。

## 十、总结：一句话说清楚 LLM Agent

**LLM Agent = LLM + 循环 + 工具 + 记忆 + 规划**

- **LLM** 是大脑，负责理解和推理
- **循环** 让它能反复「思考-行动-观察」，直到任务完成
- **工具** 让它能读写文件、执行命令、调 API
- **记忆** 让它能跨对话记住上下文和偏好
- **规划** 让它能把大目标拆成小步骤，动态调整

MCP 这类协议解决的是「工具怎么接入」的标准化问题，让 agent 的手脚更灵活、生态更开放。

Agent 现在还远不完美——它会选错工具、会陷入死循环、会忘记目标。但它的方向是明确的：**从「你问我答」的聊天盒子，变成能持续工作、能动手干活的智能体**。
