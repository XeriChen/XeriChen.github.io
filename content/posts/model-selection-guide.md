## 一、选型的核心维度

选模型不是选"最强的"，而是选"最合适的"。以下六个维度，按重要性从高到低排列，但具体任务的优先级不同。

### 1.1 上下文长度（Context Window）

上下文长度是模型一次能处理的输入上限，单位 token（约 0.75 个英文单词或 0.5 个汉字）。

截至 2026 年 8 月，主流模型的上下文长度分三档：

| 档位 | 范围 | 代表场景 |
|------|------|----------|
| 短 | 8k–32k | 简单问答、单函数生成 |
| 中 | 128k–300k | 中等代码库分析、单文档处理 |
| 长 | 1M（100 万） | 大型代码库、长篇文档、多文件联动 |

**实际约束：** 1M 上下文不等于能同等利用每一处信息。当上下文超过约 200k token 后，模型对早期信息的检索准确率明显下降。需要精确回忆长文档特定章节时，RAG（检索增强生成，先从文档库中检索相关片段再送入模型）往往比直接塞满上下文更有效。

### 1.2 推理深度（Reasoning Depth）

推理深度是模型在给出最终回答前，愿意花多少"思考 token"进行内部推演。

部分模型提供"思考强度"控制（如 minimal / medium / high / max），让你在响应质量和 token 消耗之间权衡。需要深度推理的任务包括：

- 多步数学证明
- 系统架构设计
- 复杂调试（从症状反推根因）
- 多约束条件下的方案权衡

不需要深度推理的任务：简单翻译、格式化、常规 API 调用生成。

### 1.3 响应速度（Latency）

响应速度以 TTFT（Time To First Token，从发出请求到收到第一个 token 的时间）和总生成时间衡量。

速度敏感场景：IDE 内嵌补全（TTFT 需 < 500ms）、交互式对话、实时翻译。

速度不敏感场景：离线批处理、代码审查、长文总结。

### 1.4 工具调用稳定性（Tool Use Reliability）

Agent 场景下，模型需要能稳定地按格式调用工具（函数调用），并在工具返回结果后继续推理。

不是所有模型都原生支持工具调用。部分模型需要依赖 prompt 工程模拟，格式容易出错。选择用于 Agent 的模型时，需确认其是否支持原生的 function calling / tool use 接口。

### 1.5 价格与可用性

价格通常按输入 token 和输出 token 分别计费。2026 年的量级：

- 旗舰推理模型：输入约 $1–3 / MTok（百万 token），输出约 $5–15 / MTok
- 中端模型：输入约 $0.1–0.5 / MTok，输出约 $0.3–1 / MTok
- 国内模型：通常比同水平境外模型便宜 50%–90%

可用性指：是否需要境外网络、是否支持国内直连、API 稳定性如何。

### 1.6 数据合规

处理敏感代码或数据时，需确认模型 API 的数据处理政策：对话数据是否用于训练、数据是否出境、是否支持私有化部署。

国内企业通常要求数据不出境，此时只能选择国内模型或支持私有部署的模型。

## 二、编码任务

### 2.1 代码生成（从描述到新代码）

**需求特征：** 给定功能描述，生成完整实现。

**推荐模型类型：** 在中等上下文（128k–300k）、中等思考强度下，大多数当前模型表现相近。代码生成的瓶颈往往不是模型能力，而是上下文是否充分（是否有相关接口定义、依赖库文档）。

**实际建议：**

- 项目内已有代码风格的延续 → 用中等上下文模型，提供足够的前文示例
- 全新功能的从零生成 → 旗舰模型略优，但差距不大；更关键的是 prompt 质量
- IDE 内嵌补全 → 优先选速度快的模型（TTFT < 300ms），而非最强模型

### 2.2 代码修改与调试

**需求特征：** 定位 bug、理解现有代码、做局部修改。

**推荐模型类型：** 这类任务需要模型理解大量上下文（整个文件、相关模块、错误日志），优先选长上下文模型或配合 RAG。

**实际建议：**

- 单文件修改（< 200 行）→ 中端模型足够
- 跨文件联动修改 → 需要 100k+ 上下文，或拆成多次对话
- 复杂调试（涉及多模块、异步、并发）→ 旗舰推理模型 + 高思考强度

### 2.3 终端 Agent 场景

终端 Agent（如 Claude Code、Codex CLI、Pi）通常需要模型：

1. 稳定调用工具（read/write/edit/bash）
2. 理解项目级上下文（多个文件、目录结构）
3. 在多轮对话中保持目标一致

**推荐模型类型：** 需确认模型支持原生工具调用。并非所有模型都支持，部分开源模型需要依赖 prompt 模拟。

## 三、长上下文任务

### 3.1 何时真正需要 1M 上下文

| 场景 | 需要 1M 吗 | 替代方案 |
|------|------------|----------|
| 分析一个 50 万行代码仓库 | 通常不需要 | 用 RAG 检索相关文件，或按模块拆分 |
| 处理一本 30 万字的书 | 需要 | 无有效替代 |
| 审查一个 200 文件的 PR | 需要 | 按文件分批审查，最后汇总 |
| 长对话（100+ 轮） | 需要 | 定期压缩上下文（/compact） |

### 3.2 长上下文的代价

1. **注意力衰减：** 模型对上下文中间部分的关注度通常高于两端。重要信息放在开头或结尾。
2. **成本线性增长：** 输入 token 数翻倍，价格翻倍。1M 上下文的单次调用成本可能是 128k 的 8 倍。
3. **响应变慢：** 处理更长的输入需要更多计算。

### 3.3 RAG 作为替代

当任务可以拆成"检索相关片段 → 回答"两步时，RAG 通常比直接塞满上下文更经济、更准确。

例如：在一个 50 万行代码库中搜索某个函数的用法。

- 直接塞：需要 1M 上下文，且模型可能找不到
- RAG：用向量数据库检索最相关的 10 个片段（约 5k token），送入模型

## 四、推理与规划任务

### 4.1 需要深度思考的场景

- **架构设计：** 给定需求，输出系统架构方案
- **复杂调试：** 从错误日志反推多步因果链
- **数学/算法：** 正确性要求严格的推导
- **多约束优化：** 在性能、成本、可维护性之间权衡

### 4.2 如何控制思考强度

2026 年的旗舰推理模型通常提供思考预算控制：

| 强度级别 | 适用场景 | 代价 |
|----------|----------|------|
| off / minimal | 简单任务、格式化 | 最快最便宜 |
| medium | 常规开发任务 | 中等 |
| high | 架构设计、复杂调试 | 慢、token 消耗高 |
| max / xhigh | 竞赛级数学、严格证明 | 最慢最贵 |

**实际建议：** 先用 medium 试，如果输出质量不够再提高。不要默认开 max，多数开发任务不需要。

### 4.3 常见误区

- "思考越久越好"：超过某个阈值后，额外思考的边际收益递减
- "推理模型一定比非推理模型好"：推理模型在简单任务上可能更慢更差，因为它在不需要思考的地方也"过度思考"

## 五、国内可用模型的实际约束

### 5.1 截至 2026 年 8 月的国内模型格局

| 模型系列 | 厂商 | 特点 | 可用渠道 |
|----------|------|------|----------|
| DeepSeek V4 系列 | DeepSeek | 推理能力强、开源、支持长上下文 | 官方 API、开源权重 |
| Qwen3 系列 | 阿里云 | 全面、工具调用稳定、多模态 | 官方 API、开源 |
| GLM-5 系列 | 智谱 | 中文理解好、Agent 能力 | 官方 API |
| Kimi 系列 | 月之暗面 | 长上下文、文档处理 | 官方 API |
| Doubao 系列 | 字节跳动 | 速度快、多模态 | 官方 API |
| MiniMax 系列 | MiniMax | 语音、对话 | 官方 API |

### 5.2 选择时的实际约束

**约束一：网络**

- 国内模型 API 通常在国内可直接访问，延迟低
- 境外模型（GPT、Claude、Gemini 旗舰版）需要境外网络，延迟高且不稳定

**约束二：数据出境**

- 企业代码上传境外模型 API 可能违反数据保护法规
- 国内模型的数据处理政策需查阅官方文档，确认是否支持"不用于训练"

**约束三：定价透明度**

- 国内模型通常按 token 计费，价格公开
- 部分模型提供包月套餐（如 Kimi 的会员），适合高频使用

**约束四：API 稳定性**

- 旗舰模型在高并发时可能限流，需要确认 QPS（每秒查询数）限制
- 国内模型在节假日或重大活动时可能调整服务

### 5.3 如何获取最新信息

模型能力变化快，本文数据可能在 6 个月后过时。建议通过以下渠道核实：

1. 官方文档（最权威）
2. 各厂商的 API 控制台（查定价）
3. 公开的第三方评测（如 LMSYS Chatbot Arena）
4. 社区反馈（GitHub issues、技术论坛）

## 六、选型决策树

以下是一个可复用的判断流程。从第一个问题开始，依次回答，落到最终选择。

```
1. 任务类型是什么？
   ├─ 代码生成/修改 → 跳到 2
   ├─ 长文分析/文档处理 → 跳到 3
   ├─ 深度推理/规划 → 跳到 4
   └─ 简单对话/格式化 → 选速度最快、最便宜的模型

2. 代码任务
   ├─ 数据能出境吗？
   │   ├─ 能 → 旗舰境外模型或国内高端模型
   │   └─ 不能 → 国内模型
   ├─ 需要工具调用（Agent）吗？
   │   ├─ 是 → 确认模型支持原生 function calling
   │   └─ 否 → 任意模型
   └─ 上下文多大？
       ├─ < 100k → 中端模型
       └─ > 100k → 长上下文模型或配合 RAG

3. 长文任务
   ├─ 总长度 > 300k token？
   │   ├─ 是 → 1M 上下文模型
   │   └─ 否 → 300k 上下文模型
   ├─ 需要精确引用原文？
   │   ├─ 是 → RAG + 中等模型
   │   └─ 否 → 直接送全文
   └─ 成本敏感？
       ├─ 是 → RAG 减少输入量
       └─ 否 → 直接送全文

4. 推理任务
   ├─ 需要最高正确性？
   │   ├─ 是 → 旗舰推理模型 + max 思考
   │   └─ 否 → 中等推理模型 + medium 思考
   └─ 实时交互？
       ├─ 是 → 降低思考强度或换快速模型
       └─ 否 → 可以开高思考强度

5. 最终校验
   ├─ API 在当前网络可达？
   ├─ 定价在预算内？
   ├─ 数据处理政策合规？
   └─ 如果不确定 → 先用最小规模测试
```

## 七、不做什么

最后列几条选型时常见的无效动作，避免读者浪费时间：

1. **不要只看 benchmark 分数。** benchmark 是标准化测试，和你的实际任务分布不同。一个在数学 benchmark 上高分的模型，在你的前端代码任务上可能表现一般。

2. **不要追最新发布的模型。** 新模型发布后，API 稳定性、文档完善度、社区工具支持都需要时间成熟。如果你的项目在赶进度，用已经验证过的模型。

3. **不要默认用最强的模型。** 旗舰模型贵 5–10 倍，多数日常任务用中端模型就够了。把旗舰模型留给真正需要深度推理的场景。

4. **不要假设一个模型通吃所有任务。** 成熟的工作流通常是"快模型处理日常任务 + 慢模型处理关键任务"，根据任务路由到不同模型。

5. **不要忽视 API 兼容性。** 如果你的工具链基于 OpenAI API 格式构建，切换模型时优先选兼容 OpenAI 接口的供应商，减少代码改动。
